# 协作组内 Workflow（v3）

[← 返回中文 README](../../README_zh-CN.md#tutorial) · [English](scoped-workflow-v3-en.md) | **简体中文**

2026-09-30：生产项目入口已接通。本文说明当前 v3 行为；同目录中的
v2 合同、研究和历史验收报告保留其原版本含义，不代表 v3 的限制。

## 使用方式

新建项目时开启 Git collaboration、选择有效的 GitHub 账号，并确认选用的
Harness/网关/模型可用。在画布中创建协作组，选择已有 Agent 作 Leader，
引用已有 Agent 作为组内业务节点。原外层 Agent 与连线不会因此被删除。
点击组节点进入组内 Workflow；使用相同的画布工具编辑连线、Loop 和布局，
通过面包屑或“返回父图”逐层返回。

根画布的协作组属性面板也可选择目标并添加出边，复用拖线的校验与撤销。
运行锁定的协作组保持不可编辑；编辑外层连线不改变组内图或共享 Agent 配置。

保存和重新加载嵌套配置时，Main 固定路由以显式根 Agent 引用及顶层组为准。
父子组共享成员不改变该投影；子组不会额外成为根图目标，错误固定边仍拒绝。

组内“进入协作组”可连接多条并行边，例如 1→2→3、4、5 三条路径。
只有组入口能发出并行边；路径内部沿用强边、弱边和 Loop 的原有语义。
子协作组也是复合节点，只有被执行时才展开其自己的入口并行路径。
“结束协作组”等待实际必要路径及其 Git 集成，无须另建 Join 节点。

运行界面的大画布在根图和所有组内复用同一个实时画布。点击 Agent 均显示
执行次数及共享 Agent 配置；组内次数依据该引用当前组执行批次，重试 epoch
不重复计数，也不借用其他范围或历史父组批次的状态。所有协作组均支持
查看子节点和进入组内，并通过同一右侧详情面板呈现状态。
拖动位置、缩放和平移按范围保留，仅影响展示；Main/Leader 提交新的布局
时采用新位置，实时增删节点、连线和选中路径效果沿用同一渲染流程。切换
范围不重建画布，且旧范围延迟到达的点击消息不会操作新范围的同名引用。

## 身份、权限和排队

- 所有引用共享同一 Agent 配置、session 与固定执行目录。组内保存配置前
  提示影响该 Agent 的全部引用；不改变各图的连线和布局。
- 同一 Agent 的有效到达按 FIFO 串行执行，不同 Agent 可并行。失败任务
  阻塞其 Agent 队列及依赖后继，不阻塞其他身份的独立路径。
- Main 管理根图；Leader 只管理所属范围和直接子组代理，管理调用不做
  业务工作。Leader 可是 Main 或其他已有 Agent，但不能兼任自己组内的
  业务节点；普通 Agent 的合法外层业务节点仍保留。
- 改图复用正式 workflow.json 提案、当前执行权限、capability 与原子提交。
  Main 的全局开关和各组 Leader 的本组开关分别控制范围，不能靠静态身份
  或开启开关在其他调用期间修改图。Leader 的配置提案复用 Main 校验，
  不能修改组外身份、权限开关或其他锁定字段。
- 同一身份被多层选作 Leader 时，管理调用也排队，不并发调用原 session。
  最大 10 个 Agent 的项目/容量约束不能通过嵌套重复获取配额。

## 分层 Git 交付

每次业务执行拥有独立分支/PR，但在该 Agent 不变的目录中安全切换分支。
Main 主工作区保持项目 main；未完成或未提交的业务证据不得强制重置。
组内成员 PR → 直接组分支；子组最终 PR → 父组分支；根组最终 PR → 项目
目标分支。外层业务 Agent 也通过独立 PR 交付到项目目标。

只有精确 provider 合并证明及本地目标同步确认后才解锁后继，后继从所属
集成分支当时的最新确认提交开始，并接收当前成功 epoch 的前驱结果。
旧报告、未合并结果与跳过工作不会被冒充成功。必要路径到 Finish 后，
受控运行时写入 `workflow-results/<groupRunId>.json` 的真实完成记录，
不用另外启动汇总 Worker，也不把“没有业务代码差异”当作虚假交付。

## 恢复与兼容边界

业务故障先交本组 Leader，再逐层父 Leader、全局 Main、用户。只有取得
全局 Main 本轮权限才可批准跳过；同一个 Main 身份作为本组 Leader 时
仍无跳过权限。跳过保持真实 skipped 状态，原 Leader 正式规划后继。
规划、弱路由与组最终交付问题另有持久记录，运行状态和只读 PR 树显示
真实等待原因，不伪造业务任务。

恢复先确认旧 native writer 已停止。已有正式报告只继续 Git；已合并但
未同步的 PR 只对账同步，不能重跑模型。冲突由已有业务 Agent 在原目录、
原 session 与保留分支中修复。暂停在原生安全点生效；取消持久撤权、确认
停机并关闭精确未合并 PR，保留分支、目录、session 和历史合并事实。

首次报告及原 Agent 的有限补做都须先确认工作目录收尾，再绑定此前缺失的
不可变报告 head。仍有 Memory 或业务文件待处理、或观察失败时，保留原
报告、结束回执和实际补做返回，由原 Agent 继续交付自己的文件；系统不
代提交，也不解除已经绑定的历史 head 或重置补做预算。

原任务补轮先检查实际 Memory 文件、已提交内容和当前 Git 状态；新的物理
调用不要求重复已经完成的工作记录。报告 head 本身不证明 Memory 已入库，
补轮的操作观察可通过真实 handoff 交还。若 Agent 决定产生新提交，即使仅
追加 Memory，也须完成新 head 自己的 PR/合并/同步，旧 PR 不覆盖它。

缺失报告 head 的只读补轮可由原 Agent 明确查询当前已交付 PR；同轮再查
历史 PR 不会覆盖该观察。若当前 PR 是原恢复 PR 之后的补充交付，必须同时
匹配原 execution/epoch 的准确 push、合并 journal、本地同步和当前 checkout，
且只有一个候选。缺任一证明则保持未绑定，不重复 Git 操作、不更换旧恢复
PR，也不改写原报告、路由、结束回执或补做预算。已经绑定的报告不走此路径。

新 Git 项目在首次原生调用前统一进入 v3，即使暂时没有组，Main 后续建组
也不改变身份。新项目中的旧平铺组可规范化为入口并行路径。已有原生
session 的 v2 运行项目继续沿原版本处理；不自动挑选历史 session 迁移，
不偷偷换目录/会话，也不允许已进入 v3 的项目降级回旧执行模式。

## 验证边界

回归覆盖实际 SQLite、生产 coordinator、受控原生入口及正式 MCP，另有
真实本地 Git/fake HTTP provider 测试。共享编辑器的实际 Chromium 验证
可按 [浏览器验收说明](../../web/acceptance/README.md) 重复。
受控 native/provider 不等于真实 Gateway/GitHub 验收；外部推送及 PR
验收仍需要用户明确授权。本次实现不更改已有服务的环境或状态目录。
