## 2. 已保留的修改

### A：漏路由后的自动恢复

处理目标：Worker 返回了交接文字，却漏掉工作流要求的下一步路由时，保留已有工作，尽量自动继续。

现在的处理流程：

1. 正常情况下由模型在原调用内提交路由；已有合法路由时不增加补救调用。一条确定性强边仍按原有规则推进。
2. 对需要 Worker 自己选择分支的情况，若本轮返回交接却没有终止控制动作，追加一次专门的补路由调用，尽量续用原会话。
3. 补调保留原交接和工作区，传入完整交接内容及合法候选。撤去工作区 MCP、额外 MCP、Skills 和搜索配置，提示模型只补控制决策。
4. Worker 补调仍漏路由或发生可进入该兜底路径的异常时，自动交给 Main；Main 使用精简上下文，从该 Worker 原有合法候选中选择下一步。
5. 缺路由使用独立的 `route-missing` 原因，记录 `routeRecovery` 的 `repairing / awaiting_main / repaired` 状态，不再把这种情况描述为达到业务失败次数上限。

已按讨论作出的收紧：移除了本轮额外加入的固定 60 秒修复超时，沿用现有 Harness 超时和取消机制；不再截取交接前 1,000 字用于补调；提示词不再把“返回交接”推断成“业务已经完成”。

边界：这不是任务成果验收机制，也不是通用断流恢复改造。取消、中断等控制仍然有效；Main 自身保留既有的有限恢复规则。用户选择了“Worker 补调失败后交给 Main”，没有采用“Worker 补调失败立即暂停”的方案，但不能保证模型持续无法给出合法控制动作时仍能无限推进。

### F：中断或结束后的可恢复成果索引

- 在 invocation 开始前记录可见工作区基线，在收尾时生成新增或修改文件的 JSON manifest。
- 记录 Agent、invocation、时间、文件路径、大小、修改时间及在扫描/读取限制内取得的 SHA-256。读取失败或达到限制时标记不完整。
- 清单使用独立 ID 保存，项目状态保留最近 50 个清单摘要；前端在相关停止状态下展示恢复清单入口。
- 文件明确标为未验收，不自动注册为正式 artifact，不声称 verifier 已通过。
- 新增读取接口：`GET /api/projects/:projectId/checkpoints/:checkpointId`。

边界：保存的是文件元数据清单，不是文件内容备份，也不冻结工作区。后续文件仍可能变化；`no_output` 仅表示该次调用没有检测到新增或修改的可见文件。扫描跳过隐藏路径、符号链接、Memory.md 和常见依赖缓存，并有文件/目录数量及 hash 读取量上限。

### G：取消归因与收尾同步

- 取消接口支持 `actor`、`reason`、`waitForSettlement`，记录取消请求时间、取消时间和收尾完成时间。
- 重复取消保留首次原因；invocation 事务回滚保留取消元数据，避免恢复成错误的“用户取消”。
- 前端区分用户取消与截止超时等原因。
- runner 及本轮收尾处理完成后记录 `cancellationSettledAt`，发出 `project.cancellation.settled` 事件。

截止监控方可使用：

```http
POST /api/projects/<projectId>/cancel
Content-Type: application/json

{"actor":"deadline-monitor","reason":"arm_timeout","waitForSettlement":true}
```

普通取消响应不代表已经完成全部收尾。需要冻结运行目录的调用方，应等待收尾选项返回或观察 settled 事件，再执行自己的快照并记录快照时间。旧客户端空请求仍默认为用户取消。

边界：这是取消原因记录和同步点，不包含新的截止监控器、预算检测器或文件快照服务。checkpoint 索引是尽力执行；冻结方仍应检查清单是否存在、是否完整及相关警告。该同步点不保证任意进程外后台写入已经停止。
