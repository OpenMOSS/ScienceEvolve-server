# Execution protocol and fidelity boundaries

This is a reconstruction of the published ScientistTwo v1 algorithm with explicitly selected parameters, embedded PaperOrchestra reference code and ScholarPeer v2 prompts. It does not assert recovery of unpublished original prompts/dependency pins or identical numerical results. `contracts.json` defines every role; `scripts/protocol.py` defines the executable control transitions. Main must not improvise alternatives to either.

## Parameters and provenance

| Setting | Value | Basis |
| --- | --- | --- |
| Initial candidates N₀ | 3 | Explicit user instruction |
| Seed pool N_seed | 6 | Implementation choice: 3 initial plus 1 for each of 3 subsequent rounds; user allows choosing seed configuration |
| Experimentation rounds | 4 total, k=0..3 | A.2 four rounds; explicitly count the initial round |
| Later candidate sets | 1 evolved + 1 unused seed | A.2; use body §3.3's initial-seed exception, never evolve from empty history |
| Successful ideas S | 4 | A.2; stop as soon as four full-set Good candidates exist |
| Limitation cycles | ≤16 | A.2; body §3.1 says exit at sufficiency or cap; preserve unresolved limitations on cap |
| Engineering | ≤2 modifications per subset/full stage | A.2; initial critic plus at most two repair/re-evaluation cycles |
| Ablation-driven refinement | ≤1 per downstream best cycle | A.2; accepted replacement still requires re-planning and executing all ablations |
| Peer loop | Initial review + ≤2 rebuttal/re-review cycles | Explicit interpretation of Table 5's Round 0/1/2; threshold 8/10 from A.2 |
| Meta refinement | ≤1 across this entire research run | A.2 review-based refinement; never reset when downstream repeats |
| Draft retries / content reflections / format repairs | 3 / 3 / 1 | Pinned PaperOrchestra ordinary writer defaults |
| Inner draft quality ensemble | 3 independent reviews + meta aggregation | Pinned `autoraters/agent_review.py`; numeric axes = rounded arithmetic mean |
| Literature expansions / probing questions | 3 / 10 | ScholarPeer v2 D.1; allocation 5+5 is an explicit implementation choice |
| Novelty scale / ties | Frozen Task rubric; stable generation order for equal scores | Scale and tie-break not published; no invented claim of an author default |

N_seed may be increased, but must cover all scheduled seed draws. `init` checks this. Other parameter changes require explicit run configuration and provenance; they describe a changed configuration, not the unchanged reference experiment. Model sampling defaults likewise follow the selected harness and are not represented as the paper's original settings.

## Scientific control graph

1. **Task preparation.** `task_setup` resolves actual human SOTA code/paper/full results, datasets, representative frozen subset, metrics/statistical tolerance, constraints, search services, publication cutoff, resources and runnable commands. It verifies the resources. Store a durable job ledger before launching external jobs. Missing input/tool access is blocked, not a scientific failure result.
2. **Limitations and seeds (§3.1).** Extract → verify. Expand without dropping earlier limitations; repeat until Sufficient or round 16. Generate h₀ → novelty, then iteratively one distinct, preferably higher-novelty candidate → novelty until all six exist. Each novelty decision uses two actually retrieved reference papers; record source/date/content evidence and rubric. Sort descending score, generation-order tie break. No seed is evaluated twice.
3. **Subset baseline (§3.2).** Baseline coding actually reproduces original SOTA on the frozen subset; spec filter must pass. Preserve E_base/C_base and commands. This is separate from human full-set SOTA reference values.
4. **Candidate implementation (§3.2–3.3).** First evaluate top three seeds. For each: subset coding → immediate spec filter → subset critic. Bad prunes; Good scales to full coding → spec filter → full critic. Engineer invokes the corresponding engineering role and real re-execution, then spec filter and critic again. A third Engineer after two engineering calls prunes as Bad. A full Good is recorded with its exact h/E/C. Failed candidate execution is Bad with diagnostic logs; resource unavailability is blocked. A spec violation is discarded, never counted as Good. Every role's response and all attempted artifacts remain in the journal, including engineering failures and discarded variants.
5. **Later rounds.** After exhausting a round's queue, Idea Evolver reads all earlier successful and failed traces and proposes one idea, plus the next unevaluated seed is queued. Every candidate follows step 4 in full. Stop at four Good candidates or four total rounds. Zero Good terminates `no_successful_idea`; otherwise Selector compares all full Good candidates across their benchmark metrics and logs, retaining a single consistent best h/E/C. No arbitrary scalar score replaces this scientific comparison.
6. **Ablation (§3.4).** Planner emits every required plan (not a fixed count); each gets an isolated copy of best, an actual coding/run and immediate spec filter. Critic sees the entire result set, then Good goes to drafting. Refine, within the one-refinement budget, invokes full engineering and spec filter; Result Comparison accepts only strictly better full results. On acceptance replace best and re-plan/re-run all ablations. On non-improvement retain old best and its valid ablations, then draft. Rejection or scientific execution failure of the trial likewise retains old best. Budget exhaustion preserves the critic's unresolved concern.
7. **Initial drafting (§3.5).** Execute the PaperOrchestra subgraph below. It consumes the selected idea, full results and complete ablations. Reference and method-code integrity repairs use true evidence before outer peer review.
8. **Review and rebuttal (§3.5).** Execute the full ScholarPeer subgraph below. If score≥8 proceed to meta review. Otherwise, while fewer than two rebuttal cycles have run, plan all supplementary experiments, execute every item in independent code copies with spec filtering, enhance the actual manuscript using their results and reviewer comments, verify references/method consistency and run a fresh complete ScholarPeer review. Never substitute a textual rebuttal for experiments; never reuse a stale review for a changed paper. Low score after budget exhaustion still goes to meta with the true score.
9. **Meta (§3.6).** Accept proceeds to final CoE checks. Refine, with the single global meta budget available, executes full engineering + spec filtering + Result Comparison. Only strictly better replaces best; then reset ablation/rebuttal budgets, re-run all ablations, drafting, ScholarPeer/rebuttal and meta. If not better or the trial fails, preserve the previous manuscript and corresponding best code and finish as `retained_previous_best`. If the new meta review requests further refinement after the budget is spent, finish as `meta_budget_exhausted`. Neither status means Accept.
10. **Integrity and export (§4.2).** Independently re-execute best's self-contained scripts, compare all reported scores using the frozen tolerance, and perform final specification audit. Verify all references through real search and all method claims against actual code; Writer corrects the manuscript and both audits repeat. Unresolved evidence defects block export. Export the exact best code/results/manuscript, full provenance, ablation and supplementary experiments, all reviews and integrity evidence. `meta_accept` describes the simulated reviewer decision, not actual conference acceptance. Stanford Agentic Reviewer is a held-out external evaluator and is never read as optimization feedback.

§4.3 frontier expansion means another research run using this exported paper/code as new input/baseline. Do not force three such runs into every Task or modify the workflow itself.

## PaperOrchestra subgraph

Selected reference: ordinary `methods/paper_writer.py`, pinned in UPSTREAM.json. ScientistTwo does not disclose its entrypoint or commit. All source and prompt files are present; SCIENCEEVOLVE replaces model invocation/session orchestration, not the algorithm. The optional upstream plotting entry is also supplied for reference; this workflow selects the ordinary writer with real figures prepared from experiments.

1. Copy ICLR 2025 style/template assets to a new draft directory; collect idea, all experimental/ablation logs and real figure assets. `draft_outline` follows the full outline prompt.
2. `draft_literature` follows `HybridLiteratureAgent`: collect introduction search directions, each related-work subsection's queries (including its fallback query), and all section citation hints. Deduplicate by section/focus; Google candidate retrieval with up to three retries per task (targeted hints return exactly one best match; exploratory tasks seek 10–15 strictly relevant papers without padding); Semantic Scholar metadata/title verification, cutoff filtering and unique registry; create BibTeX/citation_map, inject citations into outline, synthesize Introduction and Related Work. Search errors must remain visible; inability to retrieve required sources blocks rather than inventing them. Preserve task coverage when scheduling independent searches through tools.
3. `draft_figures` supplies reproducible scientific plots/method diagrams, metadata and captions using observed results. `draft_sections` uses the original section prompt, full outline, citation map, figure information and guidelines. It produces all sections and actual compiled PDF plus rendered page evidence. Actual tool dependencies (LaTeX, PDF rendering, scientific plotting, network services) are checked in Task preparation. Upstream Python utilities may be used atomically with their declared requirements; do not execute the whole writer.
4. `draft_quality` runs three times in independent sessions on the same current trial paper, using `autoraters/agent_review.py`'s knowledgeable/responsible/benign persona and complete review form. Each returns all nine numeric axes and full textual feedback. `draft_quality_merge` uses its original meta-review prompt to aggregate text; the controller overwrites all numeric axes with rounded arithmetic means of the three reviews, exactly as upstream. Unparseable aggregation falls back to the first review text while retaining numeric aggregation; unavailable resources block. No member sees another member's response. The content/format workers inspect rendered PDF pages as in the original pipeline. Keep that manuscript as baseline. `content_refine` generates a new whole manuscript and worklog using review, PDF, immutable experimental/citation material and guidelines; compile/render and review. Up to three refinements: accept if Overall increases; stop/revert if it decreases. With equal Overall, sum positive and negative deltas over axes excluding Overall/Confidence: drop>gain stops/reverts, otherwise accept and continue. A failed compile (`status:failed, failure_kind:compile`) consumes its refinement attempt and retains the old version; missing TeX (`missing_tex`) or a refinement exception (`exception`) stops the content loop and retains the old version, matching upstream. The next attempt always starts from the retained version, not the rejected trial.
5. `format_review` uses the original format prompt and actual retained PDF pages. If no issues, finish; otherwise exactly one `format_fix`, only layout changes. Keep the formatted version only on compile success; otherwise retain old manuscript. Outer technical writing failures allow up to three complete attempts; exhausting them blocks with diagnostics, never emits a nonexistent PDF.

Quality/refinement loops cannot change experimental observations. Inner PaperOrchestra quality review is distinct from outer ScholarPeer and uses its own upstream axes.

## ScholarPeer subgraph

Use the unabridged G.1–G.8 prompts in `upstream/scholarpeer-prompts.md`, adapting model/tool invocation and wrapping their outputs in the response contract. Start fresh for every manuscript version. Each role has an independent nonpersistent session. Supply `references/iclr-review-guidelines.md` for the G.8 review-guidelines input.

1. G.1 `review_summary`: extract structured contribution claims, methodology, results and evidence from the full paper.
2. G.2 `review_literature`: independent subdomain retrieval, top-tier/arXiv source quality and pre-submission date constraints. G.3 `review_expand`: three actual expansion passes, each informed by the accumulated literature.
3. G.4 `review_historian`: chronological domain narrative, milestones, current trajectory and unresolved problems. G.5 `review_baselines`: independent proactive search for missing SOTA baselines and datasets, with dates and comparability evidence.
4. G.6 two distinct query roles: five main contribution claims → five novelty/significance questions; five technical soundness probes. They use summary, full paper and domain/literature/baseline context. The question allocation is declared, not claimed to be disclosed by ScientistTwo.
5. G.7 novelty answer: one question at a time, active search; **no full submission**, only the cropped packet. `protocol.py next` removes paper/state/history from that packet. The agent must not browse the shared workspace for excluded data. This is an input protocol, not an OS filesystem security boundary. Soundness answer: full manuscript/internal evidence and supplied context, no web. Do not blend streams or let later questions copy earlier answers.
6. G.8 `peer_review`: only after all ten answers, synthesize the ICLR-formatted assessment with genuine score1–10, confidence, strengths, weaknesses and actionable questions. Keep all evidence and unknowns. The response `review` object must include `summary`, `strengths`, `weaknesses`, `questions`, `confidence` (1–5) and `rationale`; preserve any additional original review sections as well. Review score is generated by this role, never by Main or a preset fixture.

## Evidence, recovery and verification limits

Use independent immutable snapshot directories for baseline, candidates, every engineering trial, ablations, supplementary experiments and each draft. Record parent IDs and the exact best pointer in the worker report. The controller journal records every response and hash; state pointers select retained artifacts without destructive rollback. No native Agent-history rollback/Git feature is needed for this method's best-version semantics.

Completed tool runs are entered in a per-ticket ledger before worker handoff, including command, environment, job ID, exit status, timestamps, raw outputs and hashes. On SDK resume, poll existing jobs and recover completed results before submitting. Controller commit is atomic and duplicate-safe; it does not make remote experiment submission transactional. Never claim exactly-once external execution without backend idempotency support.

`blocked` returns to the same role with diagnostics. `failed` candidate coding prunes; failed ablation/rebuttal/baseline operations leave that required role pending; failed downstream refinement retains old best; failed draft technical operations follow the declared retry budgets. Intentional scientific changes after a frozen-task defect require a new run; do not mutate Task inputs mid-run or make old reviews apply retroactively.

The controller checks contracts, count bounds, file presence/hashes and all branch decisions. It cannot prove that an LLM's scientific judgement is correct or that a log represents a real external execution. Actual evidence audits and real research runs remain necessary. Tests use explicit fixtures solely to exercise transitions; they are never packaged as research results.
